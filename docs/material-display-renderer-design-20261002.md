### HISTORICAL renderer-local design and then-unresolved cases

`minimumDisplayGeneration` is global to the component, matching the coordinator's full-order generations. Every repricing/input begins by setting it to the current generation; only a strictly newer snapshot can supply progress rows. Thus editing A suppresses the old generation for A AND B. This is conservative hiding, not per-part cancellation and not independent per-part progress continuity. `displayIntents` is per PartId and contains only copied requested material/color/quantity/build configuration; a row is hidden while that tuple differs from the currently accepted part. Coordinator context/generation already binds upload/reference/hash; the component does not reread remote state.

Quantity input removes any older in-flight intent for that part and marks quantity pending. Input-only rows stay hidden; once an actual change requests a tuple, rows are eligible only when accepted Part.Configuration matches it and the generation is newer than the cutoff. Requests are serialized by coordinator stateGate, but renderer events can queue newer intentions while an older await is incomplete. Intents clear only once repricing activity reaches zero. The current code does NOT cancel queued older accepted mutations or prevent their protected writes; it only suppresses incorrectly labeled display rows.

Validation occurs before stateGate in the coordinator. The renderer records intent/cutoff before validation, so a rejected new input can temporarily hide still-valid display but must not be described as final quote invalidation or an accepted mutation. Existing final comparison fallback is allowed only outside repricing/pending quantity input. This fallback and clearing the entire intent dictionary need real supersession schedules; eight HtmlRenderer controls do not prove them.

Independent concern for test-first inspection: existing `CanEnterReview` depends only on final Configured+OrderQuote, not pending renderer input.
